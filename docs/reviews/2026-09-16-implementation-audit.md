## Замечания к коду

### R1 · P1 — применение удаляет независимый сигнал

[apply.ts:66](../../packages/review-engine/src/apply.ts#L66): сигнал, полностью попавший в заменяемый диапазон, удаляется через `return []`. Обычный сценарий: исходник `кот`, правка `кот → кит`, комментарий на слове `кот`. После применения комментария больше нет в sidecar. Это противоречит §6/§9 спецификации: потерявший привязку сигнал должен сохраняться.

Подтверждено `engine-repro.mts`: `signal-after-apply 0 expected 1`. Существующий тест `apply.test.ts:98` закрепляет ошибочное удаление; зелёный набор поэтому не свидетельствует о выполнении требования. Исправление: A1.

### R2 · P1 — неудачное закрытие уничтожает несохранённую сессию

[book-service.ts:351](../../apps/desktop/src/main/book-service.ts#L351) удаляет книгу из реестра **до** успешного `session.close()`, а затем очищает главы даже при ошибке. [main.ts:161](../../apps/desktop/src/main/main.ts#L161) после отказа завершает приложение, утверждая, что черновики сохранены. Однако `ChapterSession.fail()` хранит pending-пару только в памяти; запись черновика выполняется в другом пути, `checkExternal()`.

Воспроизведение: после открытия сделать appData недоступным для записи, отправить текстовую команду, закрыть книгу. Команда и close возвращают ошибку; `getBookRoot()` уже `undefined`, в прежнем appData только `recent-books.json`, черновика нет. Таким образом, восстановление доступа уже не позволяет повторить сохранение этой сессии. Дополнительно нужно проверить очередь ещё не отправленных renderer-команд и macOS window-close: ожидания только main-очереди недостаточно. Исправление: A2.

### R3 · P1 — неразрешённый журнал восстановления теряется при следующей записи

[book-service.ts:396](../../apps/desktop/src/main/book-service.ts#L396) лишь логирует `external-change`, затем открывает книгу для записи. `writePairImpl()` записывает новый журнал по тому же ключу и после успешной записи удаляет его.

Воспроизведение: прервать запись после `prepared`, внешне изменить Markdown до третьей версии, открыть книгу, изменить заметку. Результат: команда `accepted`, число журналов `0`. Исходная операция и её before/after больше недоступны. Спецификация требует разрешить незавершённую операцию **перед продолжением записи**. Исправление: A3.

### R4 · P2 — применение делает соседнюю активную правку неоднозначной

[apply.ts:48](../../packages/review-engine/src/apply.ts#L48), также строка 63 для сигналов: записи перед заменой сохраняют старый anchor, включая `source_sha256` и контекст. Собственная известная замена затем ошибочно обрабатывается как внешнее изменение и запускает текстовый поиск.

Воспроизведение: `aa bb`, правки `aa → X` и `bb → aa`; применить вторую. Первая становится unavailable, производный текст `aa aa` вместо `X aa`. Нужно обновлять anchors всех сохранившихся активных диапазонов, в том числе с нулевым сдвигом. Исправление: A1.

### R5 · P2 — редактирование сигнала меняет его UUID

[book-service.ts:483](../../apps/desktop/src/main/book-service.ts#L483): существующий сигнал удаляется, затем `addSignal(..., randomUUID())` создаёт новую идентичность. Правка комментария/типа должна сохранять ID; иначе повторный обмен с другой копией книги может превратить изменение в удаление и добавление. Подтверждено service-repro: UUID до и после не совпадают. Исправление: A4.

### R6 · P2 — папка с sidecar, но без manifest получает новые UUID

[book.ts:134](../../packages/book-storage/src/book.ts#L134): ветка отсутствующего manifest создаёт новые идентификаторы, не проверяя имеющиеся sidecar. Существующие главы рецензии перестают соответствовать новому manifest. План C5 прямо требовал read-only ошибку идентичности. Воспроизведение с валидным sidecar и заметкой: `openBook()` успешно создаёт новый manifest вместо отказа. Исправление: A5.

- Уточнить реальную проверенную ревизию Pad при завершении A6; текущий контрактный baseline не менять на непроверенный зелёный релиз.

- Стандартный `npm run test:desktop` пропускает performance; README уточнён.
