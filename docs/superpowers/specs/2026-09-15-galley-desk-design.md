# Galley Desk — спецификация первой версии

Дата: 2026-09-15. Статус: рабочая спецификация; решения уточнены после совместного review 2026-09-15.

## 1. Назначение и согласованные решения

Galley Desk — desktop-приложение для рецензирования Markdown-книг через правки и сигналы, совместимые с Pocket Editor. Рецензент читает книгу и создаёт правки/сигналы, не трогая исходный Markdown; автор — тот, кому передаётся та же папка — решает, применить их или отклонить. Одно и то же приложение обслуживает обе роли; папка книги переносится между людьми как единица передачи.

- Проект: `/home/inky/Development/galley-desk`.
- Основные платформы: Linux и macOS.
- В рамках реализации разрешены необходимые изменения Galley Editor, Galley Pad и Pocket Editor; существующее поведение этих проектов не является неизменяемым ограничением. Изменения контрактов выпускаются и проверяются согласованно.
- Стек: Electron, React, TypeScript; Galley Editor на CodeMirror 6.
- Пользователь выбирает конкретную папку книги. Приложение сохраняет список последних открытых папок. Автоматического поиска книг нет.
- Обычный ввод создаёт правки в sidecar; исходный Markdown не меняется.
- Пользователь может вручную применить отдельную правку: обновить Markdown и удалить применённую запись из sidecar.
- Основной вид показывает исправленный текст с ненавязчивыми отметками изменений. Сравнение показывает вставки и удаления.
- Для создания правки не нужны предварительное выделение и отдельная форма. Выделение служит для создания сигналов: диапазон открывает flyout с типами сигнала (`note`, `change_required`, `warning`, `review`), выбор типа открывает попап для комментария сигнала. Обычные операции копирования и клавиатурной навигации остаются доступны.
- Сигнал, комментирующий добавленный текст, привязывается к исходному диапазону соответствующей правки. В Pocket Editor он относится ко всему этому диапазону.

## 2. Предлагаемые границы первой версии

Полный рабочий сценарий: открыть папку, выбрать главу, читать и редактировать, оставить комментарий, сохранить, повторно открыть книгу в Galley Desk и Pocket Editor без потери данных.

Включены:

- последние папки, оглавление, восстановление главы и позиции;
- фильтр оглавления по названию и поиск текста текущей главы без замены; поиск по всей книге отложен;
- открытие существующего манифеста; создание совместимого манифеста для папки без него;
- умный ввод, повторное редактирование правок, Undo/Redo;
- все четыре типа сигналов Pocket Editor, комментарии и заметка главы;
- просмотр исправленного текста, сравнения и исходного Markdown;
- применение и отклонение отдельной правки;
- автосохранение, восстановление после сбоя, обнаружение внешних изменений;
- состояния устаревших и неоднозначных привязок: запись не удаляется автоматически и показывается как требующая внимания; ручного перепривязывания нет, только удаление и создание новой записи.

В первую версию не включены рекурсивный поиск книг, собственная облачная синхронизация, ИИ-функции, совместное редактирование в реальном времени и массовое применение правок. Исходный Markdown доступен для просмотра; прямое авторское редактирование — отдельная будущая возможность.

## 3. Рабочее окно

- Слева — оглавление, поиск и индикаторы рецензий. Панель сворачивается.
- В центре — текст с регулируемой шириной строки и размером шрифта. Основное место редактирования: и текста, и правок, и сигналов.
- Справа — навигация по рецензии главы: список правок и сигналов для перехода между ними и общие управляющие действия (например, счётчики по типам). Панель не содержит собственных форм редактирования; выбор записи открывает её попап в редакторе. Недоступная запись без позиции в тексте открывает карточку с сохранённым текстом, причиной недоступности и действием удаления прямо из списка, без фиктивного перехода к anchor.
- Вверху — название книги, виды «Текст / Сравнение / Исходник», состояние сохранения. Ввод текста доступен только в «Тексте». «Сравнение» позволяет просматривать записи и применять/отклонять правки, но не редактировать текст сравнения; «Исходник» полностью read-only.
- Заметка главы открывается кнопкой «Заметка главы» в правой панели, редактируется в отдельном попапе и сохраняется в `chapter_note`.
- Поиск текущей главы ищет в Markdown выбранного представления: исправленном в «Тексте», исходном в «Исходнике». В «Сравнении» ищет в исправленном Markdown и переходит к соответствующему месту. Подпись поля показывает область поиска; доступны следующий/предыдущий результат и счётчик. Комментарии и заметка главы в этот поиск не входят.
- Отметка правки в тексте — иконка карандаша. Отметка сигнала — иконка молнии, в цвете своего типа. Цвета типов сигналов повторяют `ReviewColors` из Pocket Editor (`/home/inky/Development/pocket-editor/app/src/main/java/net/inkyquill/pocketeditor/ui/theme/Color.kt`): `note`, `change_required` (`changeNeeded`), `warning`, `review`, отдельно для светлой и тёмной темы. Обе отметки видны в видах «Текст» и «Сравнение»; вид «Исходник» остаётся немаркированным сырым Markdown.
- Клик по иконке правки или сигнала открывает попап прямо в редакторе рядом с anchor: исходный/предложенный варианты и действия «Применить», «Отклонить» для правки; текст комментария и тип для сигнала. Переход из правого списка навигации к записи скроллит редактор и открывает тот же попап.
- Удаление имеет видимый маркер, даже если исправленный текст не содержит удалённого фрагмента.
- Выделение текста открывает flyout с кнопками типа сигнала (`note`, `change_required`, `warning`, `review`, каждый в цвете своего типа). Выбор кнопки открывает тот же попап для ввода комментария сигнала; комментарий отображается как небольшая подстрока под привязанным диапазоном в редакторе, рядом с иконкой молнии.
- Zen-режим скрывает левую и правую панели и верхнюю строку; текст центрируется с увеличенными полями по краям для комфортного чтения/письма. Иконки правок/сигналов, подстроки комментариев и попапы редактирования по клику остаются доступны. Есть заметный способ выйти из Zen-режима (сочетание клавиш и/или небольшой постоянный переключатель).

Если недавняя папка недоступна, запись сохраняется; доступны смена расположения и удаление записи из списка. Удаление записи не удаляет файлы.

## 4. Папка книги и совместимость

Канонические документы:

```text
Книга/
  .pocket-editor.json
  01.md
  01.review.json
  02.md
  02.review.json
```

Главы — непосредственные дочерние Markdown-файлы. Начальное обнаружение и порядок должны повторять алгоритм Pocket Editor, включая нормализацию путей, ignored_files и существующие идентификаторы. В существующем манифесте сохраняется заданный порядок.

Авторитетные исходные контракты:

- `/home/inky/Development/pocket-editor/schemas/manifest-v1.schema.json`;
- `/home/inky/Development/pocket-editor/schemas/review-v1.schema.json`;
- Kotlin-сериализаторы, AnchorFactory, AnchorResolver и EditValidator;
- существующие fixtures и тесты контрактов Pocket Editor.

Совместимость означает совпадение структуры и семантики: UUID, значения по умолчанию, типы сигналов, диапазоны и контекст anchors, хеши, порядок глав, правила активации правок и обработка неоднозначности. Схемы v1 не расширяются дополнительными полями Galley Desk.

### Терпимое чтение рецензий в обоих приложениях

Структурная корректность документа отделяется от возможности использовать отдельную запись на текущем исходнике. Pocket Editor дорабатывается вместе с Galley Desk:

- Устаревшие и неоднозначные правки/сигналы сохраняются и доступны в списке рецензии как недоступные. Они не блокируют чтение и сохранение остальных записей; ручного перепривязывания нет в обоих приложениях.
- Пересечение сохранённых диапазонов не является причиной отвергать весь sidecar при чтении или записи. Диапазоны могут относиться к разным версиям исходника. Проверка пересечений выполняется после разрешения anchors на текущей версии.
- Если разрешённые диапазоны правок пересекаются, все участники пересечения показываются как конфликтующие и исключаются из производного текста и применения. Сигналы могут пересекаться. Остальные правки работают.
- Создание и изменение активной правки по-прежнему проверяет исходные байты, хеши и отсутствие пересечения с другими активными правками. Недоступные записи не резервируют старые числовые диапазоны в новой версии.
- Сохранение сохраняет UUID и содержимое недоступных записей; их удаление выполняется только явным действием. Отсутствие текущей главы само по себе не повод удалять её рецензию.

Это изменение семантической валидации, не JSON-формы v1: пересечения не запрещены опубликованной JSON Schema. Нужны изменения чтения/записи, проекции, mutation validation и UI Pocket Editor, а не только снятие одной проверки в `ReviewJson`. Старые версии Pocket Editor могут отвергать такие файлы; совместимость гарантируется с обновлённым выпуском, его минимальная версия фиксируется при интеграции.

Повреждённый JSON, неизвестная версия и структурно некорректные записи не приравниваются к висящим anchors: исходный файл сохраняется без перезаписи. Произвольное восстановление повреждённого JSON не входит в v1.

Markdown хранится с точными исходными байтами. Нельзя молча нормализовать Unicode или переводы строк. Код редактора использует UTF-16 позиции; sidecar — UTF-8 byte offsets. Нужен явный слой преобразования координат, учитывающий переводы строк. Форматирование JSON повторяет правила Pocket Editor.

Неизвестная версия или некорректный документ не перезаписывается. Пользователю показывается причина, чтение исходника остаётся доступным.

## 5. Модель умного редактирования

Хранятся исходные байты главы, записи рецензии и производный редактируемый текст. Производный текст строится только из разрешённых, валидных, непересекающихся правок.

Каждая транзакция CodeMirror переводится в изменение набора правок. Нельзя выводить идентичность правок только из нового глобального diff: необходимо сохранять UUID существующих правок, связи с комментариями и происхождение изменённых фрагментов.

- Ввод в исходный текст создаёт правку.
- Ввод внутри правки обновляет её.
- Возврат к исходному содержимому удаляет правку.
- Изменение через границы нескольких правок требует их согласованного объединения без пересекающихся диапазонов. Связанные сигналы сохраняются с покрывающим диапазоном там, где соответствие однозначно; иначе сигнал показывается как требующий внимания (см. §6, шаг 4) без автоматического перепривязывания.
- Вставка, удаление, перенос строки, paste и форматирование проходят через одну модель транзакций.
- IME composition не прерывается сохранением или перерисовкой.
- Undo/Redo восстанавливает согласованные текст, набор правок и положение курсора. Смена главы не смешивает истории документов. Все истории Undo/Redo существуют только в памяти в рамках открытой книги; закрытие книги/проекта, выход или перезапуск приложения очищает их. Восстановление черновика после сбоя не восстанавливает Undo.

### Ограничения v1

`before` и исходный диапазон правки должны быть непустыми. Вставка кодируется заменой соседнего исходного фрагмента с сохранением его текста в `after`. Выбор диапазона должен учитывать соседние правки, границы Unicode и начало/конец файла.

Для полностью пустого исходного файла такая вставка непредставима в v1. В первой версии создание правки в пустой главе недоступно с явным объяснением причины. Расширение формата требует отдельного согласованного изменения Pocket Editor и не маскируется под v1.

Сигнал, привязанный к полностью добавленному тексту, получает исходный anchor правки. Точное выделение внутри вставки не является переносимой частью формата и не обещается после повторного открытия. Сигнал на диапазоне, затрагивающем исходный и добавленный текст, использует покрывающий исходный диапазон.

## 6. Применение правки

Ручное применение выполняется по текущей проверенной ревизии исходника и sidecar:

1. Повторно прочитать документы и проверить ожидаемые хеши и валидность выбранной правки.
2. Подготовить новые байты Markdown: заменить только подтверждённый диапазон.
3. Удалить применённую запись; перенести оставшиеся привязки (правок и сигналов) через известное преобразование исходника и пересчитать хеши и контекст там, где соответствие однозначно. Для активных непересекающихся правок на проверенной общей базе перенос детерминирован, включая смежные диапазоны: используется известная замена и сдвиг байтов, а не поиск похожего текста. Сигналы, пересекающие замену, переносятся только там, где известна принадлежность сохранившегося текста; при изменении их диапазона обновляются также `selected_text` и `selection_sha256`.
4. Для правок и сигналов, для которых однозначного соответствия больше нет, сохранить исходные anchors и показать их как требующие внимания. Не удалять записи автоматически: перепривязывания нет, единственное доступное пользователю действие — удалить запись и при необходимости создать новую правку или сигнал.
5. Проверить структурную корректность целевых документов и активных диапазонов. Записать журнал восстановления и обе подготовленные версии; выполнить замену файлов; подтвердить завершение операции.

Замена двух файлов не является одной атомарной операцией файловой системы. Журнал хранит базовые и целевые версии/хеши, чтобы после сбоя определить, какие шаги завершены. Восстановление не применяет изменение дважды и не перезаписывает неожиданную внешнюю версию. Перед продолжением записи незавершённая операция разрешается.

Применение правки создаёт границу обычной истории ввода: прежние редакторские транзакции нельзя воспроизводить поверх новой базы. В интерфейсе применение обозначено как запись в исходный файл; резервная версия сохраняется для восстановления.

Применение имеет отдельный линейный стек Undo/Redo текущей главы. В виде «Сравнение» доступны кнопки «Отменить применение» / «Повторить применение»; это контекст работы с историей применения, без отдельной роли автора. В виде «Текст» сочетания отменяют ввод. При фокусе в поле комментария, заметки или поиска они всегда относятся к этому полю.

Undo применения восстанавливает согласованную пару Markdown + sidecar до операции, включая все перенесённые anchors, сигналы и удалённую правку; Redo — пару после операции. Обе команды проверяют текущую ревизию и используют тот же механизм записи и восстановления, что применение. Последовательные применения образуют один стек. Новая обычная мутация главы (ввод, изменение сигнала/заметки, отклонение/удаление записи) или внешнее изменение завершает этот стек, чтобы откат снимка не удалил более позднюю работу. Применение очищает историю обычного ввода этой главы. В интерфейсе недоступная отмена не вызывает скрытого переключения на другой стек.

| Действие | Linux | macOS |
| --- | --- | --- |
| Undo в текущем контексте | Ctrl+Z | Cmd+Z |
| Redo в текущем контексте | Ctrl+Shift+Z, также Ctrl+Y | Cmd+Shift+Z |
| Поиск в главе | Ctrl+F | Cmd+F |

Закрытие книги/проекта очищает оба стека всех глав. Файлы восстановления нужны для незавершённых операций и не являются постоянной пользовательской историей Undo.

Отклонение удаляет правку, сохраняя Markdown и связанные сигналы: сигналы хранятся в sidecar независимо от правок (отдельный массив `signals` в `review-v1`) и не удаляются вместе с правкой, даже если создавались через «Добавить сигнал» на её диапазоне.

## 7. Сохранение и внешние изменения

Файлы книги — переносимый источник истины. Настройки окна, последние папки, позиция чтения, черновики и журнал восстановления находятся в каталоге данных приложения.

- Автосохранение работает последовательно для каждой главы; более старая запись не может завершиться поверх новой.
- После ошибки сохранения черновик сохраняется локально, интерфейс не показывает ложное «Сохранено».
- Watcher — сигнал перечитать данные, а не доказательство их актуальности. Нужны повторные проверки при возвращении фокуса и перед записью.
- Одновременное редактирование из нескольких мест не является рабочим сценарием v1; полноценного UI слияния версий нет. Автосохранение ставится в очередь после каждой транзакции и не означает немедленно завершённую запись. «Сохранено» показывается только для подтверждённой текущей ревизии.
- Внешняя версия перечитывается автоматически, когда нет ожидающей/неудачной локальной записи и незавершённой операции применения. При наличии локальной работы запись приостанавливается, её текст и sidecar сохраняются в отдельный локальный черновик. Короткое уведомление предлагает открыть внешнюю версию после сохранения черновика или сохранить локальную копию в выбранную папку. Автоматического затирания какой-либо версии и сложного интерфейса слияния нет. Если сохранить черновик не удалось, он остаётся в памяти и автоматическое переключение не выполняется.
- При закрытии книга дожидается очереди записи; ошибка не маскируется закрытием. Принудительное закрытие ОС покрывается последним успешно сохранённым черновиком, без обещания сохранить ещё не записанные на диск нажатия.
- Внешнее изменение разрешает anchors через точный алгоритм Pocket Editor: проверить `selection_sha256` по `selected_text` сигнала или `before` правки; при совпадении `source_sha256` проверить сохранённый диапазон; иначе искать точные вхождения текста, а несколько вхождений уточнять prefix/suffix. Fuzzy-поиска нет. Неразрешённые записи остаются недоступными; после разрешения проверяются пересечения активных правок. Это другой механизм, чем детерминированный перенос собственной замены в §6.
- Статус доступности вычисляется относительно текущего исходника, в JSON v1 постоянного флага «привязка утрачена» нет. При повторном открытии запись может разрешиться по единственному точному совпадению в другом месте. Для v1 принимается это ограничение общего алгоритма; изменение политики разрешения выполняется согласованно в обоих приложениях, без скрытых локальных флагов или фиктивных хешей.
- Собственные операции приложения сериализуются; открытие одной книги в нескольких окнах не создаёт независимых писателей.

Журнал и резервные пары документов обеспечивают завершение/восстановление операции на том же компьютере. Папку передают после завершённого сохранения; удобной точкой передачи является закрытие книги. Передача папки в момент аварии или незавершённой записи не гарантирует согласованную пару файлов на другом компьютере. Переносимый журнал и распределённая транзакция с облачным клиентом не входят в v1. Недоступные записи читаются терпимо, но это не заменяет отсутствующий журнал.

## 8. Границы модулей

Предлагаемая структура одного репозитория:

```text
apps/desktop/             Electron main, preload и React UI
packages/pocket-format/   документы, anchors, валидация, fixtures
packages/review-engine/   проекция текста, транзакции, правки, история
packages/book-storage/    файловые операции, ревизии, журнал, восстановление
```

`pocket-format` и `review-engine` не зависят от React или Electron. Доступ к диску находится в main process за узким типизированным IPC API. Renderer работает с включённой изоляцией контекста, без Node integration. Markdown и локальные ресурсы не получают права на исполнение произвольного кода.

Galley Editor остаётся отдельной библиотекой в `/home/inky/Development/editors/galley-editor`, публикуется в npm как `@inkyquill/galley-editor`; приложение использует фиксированную версию из npm. Galley — half-WYSIWYG редактор с live preview (Obsidian-style): решения о рендеринге не должны молча менять модель позиций документа. Galley предоставляет позиции и транзакции своего Markdown-документа в UTF-16 (в том числе уже существующий `getSelection()`); это не пиксельные координаты. Galley Desk сопоставляет позиции производного Markdown с канонической главой, а форматный модуль переводит их в UTF-8 bytes. Сначала проверяется существующий публичный API; недостающие общие возможности добавляются в Galley, без знания о канонической главе Pocket Editor.

Общие исправления ввода, рендеринга и команд делаются в Galley Editor и полезны широкому кругу потребителей; специфичные для Pocket Editor знания (anchors, сигналы, правки) остаются в Galley Desk и реализуются через overrides и публичный API Galley, не патчами внутри библиотеки. Связь review-engine с CodeMirror/Galley оформляется отдельным адаптером.

Цвета и настройки шрифта светлой/тёмной темы выносятся в отдельный публикуемый пакет `@inkyquill/galley-themes`, пригодный не только для Galley Pad и Galley Desk, но и для других потребителей Galley Editor. Начальные палитры и структура токенов (`app`/`editor`/`markdown`/`syntax` и т. п.) берутся из `/home/inky/Development/galley-pad/src/themes/tokens.ts` и `catalog.ts` как отправная точка, а не общий рантайм-код Galley Pad: сам Galley Pad остаётся отдельным приложением. Пакет живёт в репозитории `/home/inky/Development/editors/galley-editor` рядом с самим Galley Editor (репозиторий становится небольшим workspace-монорепо: `packages/galley-editor`, `packages/galley-themes`), так как темы не имеют смысла без Galley Editor и версионируются вместе с ним. Это предварительная работа в отдельном репозитории, не часть кодовой базы Galley Desk.

Совместная разработка использует собранные локальные npm-архивы (`npm pack`) Galley Editor и тем с временной установкой в Galley Desk; абсолютные `file:`-пути не попадают в релизные зависимости. Интеграционная проверка может собрать архивы из зафиксированных ревизий соседних репозиториев в CI. Для обычных сборок публикуются совместимые версии и фиксируются версии/lockfile. Galley Pad переводится на общий пакет тем и проверяется как существующий потребитель; его приложение не переносится в Galley Desk.

Версии зависимостей выбираются по актуальной совместимости при scaffold и фиксируются lockfile. CI получает Pocket Editor по зафиксированному commit, а не по абсолютному пути разработчика; для настоящих Kotlin ↔ TypeScript проверок устанавливает JDK и необходимые Gradle/Android SDK компоненты существующего проекта. Отдельная переработка Android-проекта в библиотеку ради тестов не требуется.

## 9. Проверки и критерии готовности

### Контракты

- Kotlin читает документы, записанные TypeScript, и наоборот.
- Совпадают anchors и хеши для кириллицы, emoji, комбинируемых символов и LF/CRLF.
- Сохраняются UUID, сигналы, заметки, порядок и ignored_files.
- Неподдерживаемые документы не перезаписываются.

### Редактор

- Вставки в начало/конец, удаление, замена, переносы, paste, форматирование.
- Повторное редактирование правки, объединение диапазонов, возврат к исходнику.
- Undo/Redo (история ввода) и сигналы, привязанные к исходному и добавленному тексту.
- Создание сигнала: выделение → flyout с типом → попап комментария → запись в sidecar с верным типом, цветом и иконкой молнии.
- Регрессии Galley закрепляются воспроизводящими тестами при исправлении; проверяется и существующее поведение Galley Pad.

### Применение

- Undo/Redo применения восстанавливает полную пару Markdown + sidecar, включая anchors остальных записей; сочетания и приоритет полей ввода соответствуют §6.
- Последовательные применения отменяются по порядку; обычная мутация/внешняя версия завершает стек. Закрытие и повторное открытие книги очищает все Undo/Redo.
- Смежная активная правка переносится точно. Потерявший диапазон сигнал и ранее недоступная правка сохраняются без ручного перепривязывания.
- Сохранённые диапазоны недоступной и перенесённой правки могут пересекаться: оба приложения читают и сохраняют файл. При пересечении разрешённых диапазонов все участвующие правки конфликтующие, остальные остаются рабочими.

### Диск

- Отказ записи, внешнее изменение, повторное открытие.
- Внешнее изменение без локальной работы перечитывается автоматически; во время ожидающей/неудачной записи сохраняется локальный черновик без затирания внешней версии. Ошибка сохранения черновика не уничтожает работу в памяти.
- Сбой после каждого шага применения с последующим восстановлением.
- Изменённый внешний файл во время восстановления не теряется.

### Интерфейс

- Поиск и фильтр оглавления соответствуют §3; переход к результату работает после правки. Заметка главы сохраняется/читается обоими приложениями.
- «Исходник» и текст «Сравнения» не принимают ввод; недоступная запись открывается из списка даже без позиции в тексте.

- Zen-режим: иконки правок/сигналов, подстроки комментариев и попапы редактирования по клику остаются рабочими при скрытых панелях; выход из режима работает.
- Светлая/тёмная тема через `@inkyquill/galley-themes` применяется корректно и не тянет Galley Pad как зависимость в рантайме.

### Desktop

Vitest для чистой логики, интеграционные тесты файлов на временных папках, Playwright для desktop-сценариев. Клавиатуру, IME, буфер обмена, масштабирование и файловые диалоги проверить на реальных Linux и macOS. Успех браузерных тестов не заменяет проверку packaged-приложения.

Основной критерий: активная, недоступная и конфликтующая записи проходят цикл Galley Desk → обновлённый Pocket Editor → Galley Desk без потери; ручное применение обновляет Markdown, удаляет только применённую запись и сохраняет остальные данные.

### Практический ориентир производительности

Начальный проверочный набор: книга до 100 глав, открытая глава до 1 MiB UTF-8 и 500 записей рецензии. Загружается редактор одной главы, а не вся книга в DOM. На согласованной тестовой машине целевой p95 от ввода до отображения — не более 50 мс без учёта завершения записи на диск; обычное открытие такой главы после запуска — до 2 секунд. Это цели проверки, не запрет на большие книги и не заявление о достигнутой производительности. Фиксируются машина, release-сборка, задержки и память; отдельный универсальный лимит RAM до измерений не вводится.

## 10. Последовательность реализации

1. Scaffold desktop-приложения и пакетов, CI с Node/JDK и инструментами Kotlin-проверки, минимальные сборки Linux/macOS.
2. Терпимое чтение/запись, проекция и UI недоступных/конфликтующих записей в Pocket Editor; совпадающая реализация Galley Desk и общие fixtures. Проверка координат. Необходимые общие API Galley, извлечение тем и подключение Galley Pad выполняются в соответствующих репозиториях до потребляющих их этапов.
3. Открытие папки и главы, Galley, создание и сохранение одной правки.
4. Повторное редактирование, история, сигналы (с flyout и комментарием).
5. Применение, перенос anchors для правок и сигналов, свой Undo/Redo применения, журнал и восстановление.
6. Внешние изменения (автоперечитывание или сохранение локального черновика), последние папки, правая панель навигации рецензии, Zen-режим, `@inkyquill/galley-themes` и packaged-проверки.

Каждый этап заканчивается проверяемым сценарием. Связанные изменения в Pocket Editor, Galley Editor и Galley Pad входят в работу, но сохраняют границы репозиториев. Детальный план реализации опирается на эту спецификацию и не требует повторно согласовывать уже принятые решения.
